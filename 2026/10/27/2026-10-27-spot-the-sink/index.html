Spot the Sink: A Daily Secure Code Review Game

How I built a Wordle-style daily game for secure code review that grades fixes with hidden tests running in the player's browser, on Cloudflare's free plan.

Spot the Sink: A Daily Secure Code Review Game

Wordle works because it is small: one puzzle a day, the same for everyone, a result you can share in a single line. I wanted that for secure code review. So I built Spot the Sink.

Every day there is one short, realistic snippet with a vulnerability in it. You do three things:

  1. Spot the vulnerable line (or lines). Some of the lines are decoys that look dangerous and are not.
  2. Name the weakness by picking the right CWE.
  3. Fix the code. Hidden exploit and functional tests run against your fix, and you only get the points if the exploit is blocked and the feature still works.

Then you get a score out of 100, a diff against the reference fix, a short writeup, and a share line like Spot the Sink #12 ■▣□.

Why a game

Most security training is either a slide deck or a full lab. Neither fits into a coffee break. Reading code and noticing the one line where untrusted input reaches something dangerous is a skill, and like most skills it improves with small, frequent repetitions. A daily puzzle, a streak counter and a result you can paste into a chat were the cheapest way I could think of to make that a habit.

The three stages

Spot. The snippet is shown as clickable rows. You tap or click the lines you think are vulnerable. Pick the primary line without piling on wrong ones and you get full marks; find some vulnerable line and you get half. Selecting everything does not work, because extra wrong lines cost points.

Name. A search box over CWE ids, names and one-line descriptions. An exact match scores full marks, a closely related CWE scores half. I wanted people to learn the difference between, say, SQL injection and the broader injection class, not just to find “something with injection in the name”.

Fix. A plain editor, prefilled with the vulnerable code. “Run & submit” stays disabled until you change something, and there is deliberately no “skip”. Two hidden test suites run: the exploit tests must now fail to exploit your code, and the functional tests must still pass. Block the attack but break the feature and you get partial credit. That second suite matters, because the easiest “fix” for most bugs is to delete the feature.

The interesting part: tests run in your browser

I wanted to grade real code without running a server that executes strangers’ code. That is expensive, and it is a security problem all of its own.

So the tests run on the player’s device:

  • Python challenges run in Pyodide (CPython compiled to WebAssembly) inside a dedicated Web Worker, with pytest doing the work.
  • JavaScript and TypeScript challenges run in a plain Web Worker. TypeScript just has its types stripped first.
  • Misconfiguration challenges (Dockerfile, Docker Compose, Helm, Terraform, AWS CDK) are config files. The tests parse the submission as text, or, for CDK, run it against a small recording stand-in for aws-cdk-lib.

What the client can and cannot be trusted with

Grading in the browser has an obvious catch: the tests are visible to anyone who looks, and a determined player can forge the result. I decided to accept that for now, because there is no leaderboard and nothing to win. Cheating only spoils your own fun.

What I did care about:

  • Answers, solutions and writeups never ship in the static site. A build step scans the output and fails if it finds any of them, or any future challenge’s snippet.
  • The tests are handed out only after you commit to Spot and Name. The server records your first answers once per challenge and returns the test bundle, but no scores or feedback, so the endpoint cannot be used as an oracle to try combinations.
  • The server recomputes the Fix points itself from the reported per-test results. The client’s own verdict is only a hint for the display.

If this ever gets a leaderboard, fixes will have to be verified server-side. That is written down as a known limitation.

Built to cost nothing

The whole thing runs on Cloudflare’s free plan:

  • A static Next.js export served as Workers static assets. No server-side rendering, because the free CPU limit per request makes it a non-starter.
  • One small hand-written Worker that answers /api/* only.
  • D1 for anonymous attempts and aggregate stats (“41% spotted it”).
  • Turnstile in front of the two endpoints that record anything.

The free plan shapes the design more than I expected. Heavy parsing and validation happen at build time, not per request. The private challenge data is bundled into the Worker. Stats are cached at the edge for a minute so a popular day does not burn through D1 reads. And nothing writes to the database before Turnstile has passed, so anonymous traffic cannot use up the write quota: cheap checks first (content type, an in-memory flood limit, body size, schema), then Turnstile, then the database.

There are no accounts. Your identity is a random id in localStorage, your streak lives in your browser, and the server stores no IP addresses.

Content, and a validator that keeps me honest

Each challenge is a directory: the vulnerable snippet, a reference fix, a writeup, and the exploit and functional tests. A validator checks every one of them, on every change:

  • the functional tests pass on the reference fix,
  • the exploit tests fail on the vulnerable snippet and pass on the fix,
  • and both results are identical under plain CPython and under Pyodide in Node, so what I test on my machine is what players get in their browsers.

At the moment there are 23 original challenges across Python, JavaScript, TypeScript, Dockerfile, Compose, Helm and Terraform, shuffled and repeated for the following weeks while I write more.

A security review of a security game

It felt wrong to ship a secure-coding game without reviewing it:

  • A cache bypass: the stats cache was keyed on the full URL, so adding ?x=1, ?x=2, … would have forced a database read per request. The cache now keys on the path only.
  • A reversible IP hash: I hashed IPs for rate-limit counters, but a plain hash of an IPv4 address can be brute-forced. It is now an HMAC with a secret key.
