Email Security: SPF, DKIM, DMARC & Co.

How email authentication and encryption work: SMTP, SPF, DKIM, DMARC, ARC, MTA-STS, DANE, S/MIME and PGP, including header analysis and practical commands.

TL;DR

  • SMTP has no sender authentication built in. Everything that makes spoofing harder today was bolted on afterwards.
  • SPF checks whether the sending IP is allowed for the envelope domain. DKIM checks a signature. DMARC requires that one of the two aligns with the visible From: domain and defines what the receiver should do on failure.
  • MTA-STS and DANE protect the transport between servers, S/MIME and PGP protect the content end-to-end.

The Path of a Mail

  • MUA (Mail User Agent): the mail client.
  • MSA (Mail Submission Agent): accepts mail from the client after authentication.
  • MTA (Mail Transfer Agent): relays mail between servers. It finds the destination via the MX record of the recipient’s domain.
  • MDA (Mail Delivery Agent): stores the mail in the mailbox.

Ports and Protocols

Port Protocol Purpose
25 SMTP MTA↔MTA relay (server to server). Many ISPs and cloud providers block it for client submission, so it should not be used for that.
587 SMTP Submission + STARTTLS Client submits mail after authenticating. Classic standard for submission.
465 SMTPS (implicit TLS) Submission with immediate TLS (no plaintext handshake). RFC 8314 prefers this variant.
143 / 993 IMAP / IMAPS Mailbox access (mail stays stored on the server).
110 / 995 POP3 / POP3S Mailbox access (usually download + delete).

Envelope vs. Header-From

  • SPF checks the envelope (MAIL FROM, or HELO as a fallback).
  • DKIM checks a cryptographic signature over headers and body.
  • DMARC ties both to the visible Header-From.

The user only sees the Header-From, but SPF and DKIM initially check something else. Both sender fields can be chosen freely. Authentication only means that the claim can be verified against the DNS records of the respective domain.

Relay Types

  • Open relay: accepts mail from anyone to anyone, without auth. Historically abused by spammers, practically extinct today and blocklisted immediately (e.g. Spamhaus). An accidental open relay is a configuration error with total reputation damage.
  • Authenticated relay / smart host: only relays after login. Standard for outgoing submission.
  • Backup MX / secondary: accepts mail when the primary MX is offline and delivers it later. Risk: the backup MX often does not know the valid recipients, so it accepts everything and later produces backscatter (bounces to forged senders). Spammers also deliberately prefer it because it often filters less strictly.

Further Reputation Factors

  • Reverse DNS (PTR) / FCrDNS: the IP should point to a hostname that resolves back to the same IP.
  • DNSBLs: blocklists for IPs and domains that receivers query when accepting mail.
  • Greylisting: the receiver temporarily rejects unknown senders (4xx). Real MTAs retry, simple spam bots often don’t.

SPF (Sender Policy Framework)

SPF answers exactly one question: “May this IP send mail for this domain (in the envelope)?”

How SPF Works

  1. The domain publishes a DNS TXT record with a list of allowed sending IPs/hosts.
  2. On receipt, the receiver takes the envelope domain (MAIL FROM, or HELO) and looks up its SPF record.
  3. It compares the connecting IP with the policy and evaluates pass, fail, softfail, neutral, none, permerror or temperror.

The record is evaluated from left to right, the first match wins:

Part Meaning
v=spf1 version tag
mx the domain’s MX hosts may send
a:mail.company.example the IPs of this host may send
ip4:192.0.2.0/24 this IPv4 range may send (ip6: works the same way)
include:_spf.google.com additionally, the SPF policy of this domain applies
-all everything else: fail (reject)

Qualifiers

Qualifier Result Meaning
+ pass default if no qualifier is given
- fail not allowed, reject
~ softfail probably not allowed, accept but mark
? neutral no statement

A +all allows every sender, in practice this is a configuration error.

The 10-Lookup Limit

During evaluation SPF may cause at most 10 DNS lookups. include, a, mx, ptr, exists and redirect count. ip4, ip6 and all don’t. Exceeding the limit → permerror, and the policy no longer applies reliably. In addition, at most 2 “void lookups” (queries without a result) are allowed.

Too many include: chains exceed the limit quickly → the solution is “SPF flattening” (IPs instead of includes). The downside: if the provider changes its IPs, the flattened record becomes stale.

ptr is deprecated according to RFC 7208 (“SHOULD NOT”) and doesn’t belong in new records.

SPF Alone Is Not Enough

  • SPF checks only the envelope, not the visible From:. An attacker can display From: boss@company.example and still get an SPF pass for their own envelope domain.
  • SPF breaks on forwarding: when an intermediate server forwards the mail, the connecting IP changes → SPF fails at the destination (remedy: SRS, the Sender Rewriting Scheme).

DKIM (DomainKeys Identified Mail)

The Principle: Signing with Public-Key Cryptography

  1. The sending server computes a body hash and signs a defined set of headers with its private key.
  2. The result ends up in the mail as a DKIM-Signature: header.
  3. The public key lives in DNS under <selector>._domainkey.<domain>.
  4. The receiver fetches the public key and verifies signature and body hash → pass or fail.
Tag Meaning
a Algorithm. rsa-sha256 is common, ed25519-sha256 (RFC 8463) is rarely supported.
c Canonicalization (header/body). relaxed tolerates whitespace changes in transit.
d signing domain (checked against From: by DMARC)
s selector, determines the DNS name of the key
h signed headers. from must be included.
bh hash of the body
b the signature itself

In Practice

  • Use at least 2048-bit RSA (1024 bit is considered too weak).
  • Selectors allow key rotation: publish a new selector, switch over, remove the old one later.
  • t=y in the DNS record marks a key as “test mode”; receivers should then not treat failures harshly.

Limits and Weaknesses

  • DKIM only says “the domain d= signed this”. It does not enforce that d= matches the visible From:. Only DMARC makes that connection.
  • Mailing lists that change subject/body break the signature (→ ARC).
  • DKIM replay: a validly signed mail can be resent unchanged by an attacker to arbitrary recipients. The signature stays valid, and the reputation of the signing domain is abused.
  • The optional l= tag (body length) allows appending content beyond the signed length. It should not be used.

DMARC

DMARC is the glue: it requires that SPF or DKIM not only pass, but also be aligned with the visible From: (alignment), and it tells the receiver what to do on failure. One passing, aligned mechanism is enough for a DMARC pass.

A pass for SPF/DKIM is of little use if it refers to a foreign domain. DMARC therefore requires identifier alignment:

  • SPF alignment: the envelope domain (MAIL FROM) matches the From: domain.
  • DKIM alignment: the d= of the valid signature matches the From: domain.

Mode per check:

  • relaxed (default): the organizational domain must match (sub.company.example ≈ company.example).
  • strict: exact match required.

The DMARC Record

Tag Meaning
p policy for the domain: none, quarantine or reject
sp policy for subdomains (default: same as p)
pct percentage of mail the policy is applied to
adkim DKIM alignment: r (relaxed) or s (strict)
aspf SPF alignment: r (relaxed) or s (strict)
rua address for aggregate reports (XML, daily)
ruf address for forensic reports of individual failures (rarely supported)

Rollout

  1. p=none with rua=: only observe and use the reports to find out which systems legitimately send for the domain.
  2. Fix SPF and DKIM for all legitimate senders (newsletter tool, CRM, ticket system …).
  3. p=quarantine, first with a low pct, then increase it.
  4. p=reject for full enforcement.

A domain with p=reject can no longer credibly be spoofed directly in From:. Attackers therefore switch to lookalike domains, display-name spoofing or compromised legitimate accounts. These patterns are covered in the section Detecting Attacks.

BIMI

With p=quarantine or p=reject, a domain can additionally use BIMI: mail clients then show the brand logo next to the mail. This requires a DNS record default._bimi.<domain>, an SVG logo and, with many providers, a Verified Mark Certificate (VMC).

ARC (Authenticated Received Chain)

Mailing lists and forwarding change mail (subject prefix, footer, new IP) and thereby break SPF and DKIM. DMARC then fails even though the mail was originally legitimate. ARC (RFC 8617) solves this by having an intermediate server “freeze” the state.

A trusted intermediate server adds three headers when passing the mail on. All three carry an instance number i= (1 for the first hop, 2 for the second, and so on):

Header Function
ARC-Authentication-Results (AAR) Records what SPF/DKIM/DMARC looked like before the modification.
ARC-Message-Signature (AMS) Signature over the message as it enters this hop (DKIM-like).
ARC-Seal (AS) Signs the ARC header chain itself and links it to the previous hop.

Important: a valid ARC chain only proves that the hops passed the mail on this way. Whether the receiver believes it is decided by the receiver itself, based on a list of trusted sealers. ARC headers set by an unknown server are worthless.

Encryption

A) Transport (hop-by-hop)

  • STARTTLS: starts in plaintext and opportunistically upgrades to TLS. Problem: STARTTLS stripping. A man-in-the-middle removes the TLS announcement and the connection stays in plaintext.
  • Implicit TLS / SMTPS (465): TLS immediately, no plaintext window.
  • MTA-STS (RFC 8461): publishes via an HTTPS policy that incoming connections should enforce TLS → prevents downgrade for domains that publish it.
    • DNS record: _mta-sts.company.example TXT "v=STSv1; id=20261003T000000"
    • Policy file: https://mta-sts.company.example/.well-known/mta-sts.txt with mode: (none, testing, enforce), mx: and max_age:
    • Recommended rollout: testing first, then enforce.
  • DANE (RFC 7672; TLSA records + DNSSEC): “pins” the server certificate in DNS. Prevents downgrade/MitM, but requires DNSSEC.
  • TLS-RPT (RFC 8460): reporting channel for failed or non-enforced TLS connections. Enabled via _smtp._tls.company.example TXT "v=TLSRPTv1; rua=mailto:tls-reports@company.example".

B) End-to-End (E2E)

S/MIME PGP / OpenPGP
Trust model X.509 + certificate authorities (CA) Web of Trust / manual key verification
Adoption Enterprise, Outlook world Tech/security community, GnuPG
Setup can be rolled out centrally decentralized, more effort for users
Key discovery directory services, certificate in signed mails keyservers, WKD (Web Key Directory), Autocrypt

Shared limits:

  • Metadata is not encrypted: sender, recipient, timestamp and usually the subject are visible.
  • No forward secrecy: if the private key is compromised later, archived mails can be decrypted retroactively.
  • Server-side spam/malware scanning cannot see the content.

Rule of thumb: in companies with a central PKI, S/MIME is more practical; in technical circles and for individuals, PGP is used more often.

Detecting Attacks

Reading Headers

When analyzing a suspicious mail, these headers are worth a look (read from bottom to top, the bottom-most Received: is the first hop):

Header What to look for
Received Path of the mail, IPs and hostnames. Only hops of your own provider are trustworthy.
Authentication-Results spf=, dkim=, dmarc= of the receiving server (only trust your own server)
Return-Path Envelope sender that SPF was checked against
From vs. Reply-To If Reply-To points to a different domain, that is a classic BEC indicator
Message-ID The domain often doesn’t match the claimed sender

Typical Attack Patterns

  • Lookalike and homograph domains: company-example.com, cömpany.example (Unicode), rn instead of m. These domains can have their own SPF/DKIM/DMARC with pass.
  • Display-name spoofing: "Boss Company" <random@gmail.example>. Many clients only show the name, especially on mobile.
  • BEC (Business Email Compromise): fraud via forged or hijacked boss/supplier mail, e.g. with changed bank details. It often needs no malware.
  • Compromised legitimate accounts: mail comes from the real domain, everything is pass. Only behavioral and content analysis plus MFA help here.
  • Direct spoofing of a domain without a DMARC policy or with p=none.

In Practice: Checking and Testing Records

Other useful tools: MXToolbox, mail-tester.com and Google Postmaster Tools. DMARC aggregate reports can be analyzed with tools like parsedmarc.

Only send test mails with a forged sender against your own domains and servers, or with explicit permission.

Conclusion

Mechanism Protects against Weakness
SPF sending from unauthorized IPs checks only the envelope, breaks on forwarding
DKIM tampering with content and headers no link to From:, replay possible
DMARC spoofing of your own From: domain no effect against lookalike domains
ARC DMARC failures caused by mailing lists requires trust in sealers
MTA-STS/DANE downgrade and MitM on the transport path only effective if both sides support it
S/MIME/PGP reading and forging the content metadata exposed, laborious key management

Recommendation for your own domain: set up SPF + DKIM (2048 bit), start DMARC with p=none and reports, and tighten step by step up to p=reject. Then add MTA-STS and TLS-RPT.
